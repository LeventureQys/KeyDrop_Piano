## A. 流程与文档结构

### A1. v1.0.0 的范围界定（MVP vs 全量）【P0】

- **问题描述**：需求文档列出 7 大需求点（跨平台、读谱、原型、动画、双模式、BPM 调节、导入导出）+ 1 项调研（OTG）。其中"跨平台"本身又内含 Android / iOS / Windows 三个目标。如果 v1.0.0 把全部都做掉，规模会非常大；但你在文档开头又说"目前着重做安卓版本的"。这里需要明确 v1.0.0 的真正交付边界。
- **建议方案**：**v1.0.0 仅交付 Android 单平台 MVP**，覆盖 7 大需求中的"可玩闭环"，跨平台只在架构选型时为后续 iOS/Windows 留好抽象，不实际产出 iOS/Windows 构建产物。理由：
  - 鲁棒性：MIDI 设备接入、实时判定、动画性能本身就是高风险项，多平台并行只会让 v1.0.0 永远不能闭环。
  - 可测试性：单平台便于建立确定的验收环境（具体机型 + 具体电钢琴型号），多平台会让验收用例膨胀且无法稳定执行。
  - v1.0.0 的"可玩闭环"建议范围：
    - ✅ MIDI 文件导入 → DK 谱生成
    - ✅ DK 谱下落式播放 + 学习模式 + 演奏模式
    - ✅ 电钢琴 MIDI 实时输入判定（USB OTG，单一连接方式）
    - ✅ BPM 调节、抢拍/拖拍/掉 key 统计
    - ✅ DK 谱本地导入/导出
    - ❌ iOS / Windows 构建（仅做架构预留）
    - ❌ 蓝牙 MIDI、Wi-Fi MIDI（后续版本）
    - ❌ 云端账号、谱面分享、社区（后续版本）
- **风险预警**：
  - 若用户要求 v1.0.0 同时交付三平台，则**几乎必须**采用 Flutter / .NET MAUI 等单一代码库方案，且交付周期会显著拉长；同时 MIDI 接入在 iOS（CoreMIDI）和 Windows（WinMM/WinRT MIDI）的 API 差异会成为额外风险源。
  - 若坚持只做 Android 但仍要求"架构可平滑迁移"，需要在 v1.0.0 投入额外设计成本（接口层、MIDI 抽象层），用户需接受"架构投入 vs 当下功能进度"的权衡。
- **备选方案**：
  - 备选 B：v1.0.0 = Android + Windows（Flutter 单代码库），iOS 留到 v2.0.0。鲁棒性中等、测试用例膨胀至 2 倍。
  - 备选 C：v1.0.0 仅交付"无 MIDI 设备的演奏模式"（不连电钢琴，用触屏代替），v1.1.0 再加 MIDI 输入。鲁棒性最高、可在没有硬件的情况下验收，但偏离了"电钢琴学习辅助"的核心价值。
- **用户答复**：

## B. 技术架构

### B1. 跨平台技术栈选型【P0】

- **问题描述**：候选方案差异很大，且每个方案对 MIDI 实时性、原生 UI、动画性能的影响截然不同。
- **建议方案**：**Flutter（Dart）+ 平台通道（MethodChannel/EventChannel）调用原生 MIDI**。理由：
  - 鲁棒性：Flutter 渲染管线（Impeller / Skia）对 60fps 动画支持稳定，下落式音游对帧率敏感，Flutter 比 React Native 在动画一致性上更可控。
  - 可测试性：Dart 单元测试 + widget 测试体系完整；MIDI 平台通道部分通过 mock channel 测试。
  - 跨平台投入产出比：同一份 Dart 代码可同时覆盖 Android / iOS / Windows，符合长期目标。
  - MIDI 接入：通过 `flutter_midi_command` 等社区库，或自写平台通道直接对接 Android `android.media.midi`、Windows `winmd MIDI`、iOS `CoreMIDI`。
- **风险预警**：
  - Flutter 在 Windows 桌面端的 MIDI 生态相对较弱，可能需要自己写 FFI/通道实现。
  - 下落式动画若使用 Widget 树会有性能问题，**必须使用 `CustomPainter` + `Ticker` 直接绘制**，这一点要在 Stage 设计文档中明确。
  - 实时 MIDI 输入延迟在 Flutter 中目前最低可做到 10-30ms，**对于专业演奏者可能略偏高**，但对学习模式可以接受。
- **备选方案**：
  - 备选 B：**Kotlin Multiplatform + Compose Multiplatform**。原生 Android 体验最佳、MIDI 最直接，但 Windows 端需要 Compose Desktop（仍处于发展期），iOS 需要 Swift 桥接。
  - 备选 C：**Android 原生（Kotlin + Jetpack Compose）+ 后续各平台原生重写**。当下成本最低、性能最佳，但跨平台时几乎要重写整套。
  - 备选 D：**React Native + Reanimated**。生态丰富但动画一致性、MIDI 原生桥接稳定性都不如 Flutter，**不推荐**。
- **用户答复**：
建议方案我觉得可以

  - 价值导向：v1.0.0 的核心价值是"可玩"，账号、云同步、社区是后续增量。

- **风险预警**：若用户后续想加云端谱面市场或账号系统，需要在 v2.0.0 单独设计。本地的 DK 谱存储格式建议从一开始就设计为"可序列化、可上传"的 JSON 或带版本号的结构。

### B3. 软件分层结构【P1】

- **问题描述**：需求中提到的"前台、后台形式"如何在单 App 内分层。
- **建议方案**：采用**三层架构**：
  1. **UI 层**（Flutter Widget + CustomPainter）：原型界面、下落动画、设置界面、谱面检索界面。
  2. **领域层（Domain）**：DK 谱模型、MIDI 解析、判定逻辑、统计逻辑，**纯 Dart，无平台依赖**。
  3. **平台层（Platform Adapter）**：MIDI 设备接入、文件读写、音频输出。Android 通过 MethodChannel/EventChannel 调用原生。
  - 领域层必须可通过纯单元测试覆盖，平台层通过 mock 测试。
- **风险预警**：分层不严会导致领域层耦合平台 API，跨平台时拆不动。需要在 Stage 设计文档中明确"领域层禁止 import `dart:io` 之外的任何平台 SDK"。
- **备选方案**：MVVM / Clean Architecture 等更细的分层。**不推荐**，对 v1.0.0 规模过度设计。
- **用户答复**：
按照建议来吧，我觉得可以

## C. MIDI 与电钢琴硬件

### C1. 电钢琴接入数据流【P0】

- **问题描述**：需求 0 要求调研"电钢琴 → OTG → 手机 typeC"。需要确认 v1.0.0 支持的连接方式范围。
- **建议方案**：**v1.0.0 仅支持 USB OTG（电钢琴 USB-B → USB-C OTG 转接 → 手机）**。理由：
  - 鲁棒性：USB MIDI 延迟最低（约 1-5ms），最稳定，是大多数电钢琴的标配。
  - 可测试性：连接拓扑单一，验收环境明确。
  - **数据流路线**（调研结论）：
    - 物理层：电钢琴 USB-B 母口 → USB-B 公转 USB-C 公线缆 → 手机 USB-C 母口（手机需支持 USB OTG/Host 模式，绝大多数 2018 年后中端及以上 Android 机型均支持）。
    - 驱动层：Android 自带 USB Audio Class 2.0 + USB MIDI 1.0 驱动，无需安装第三方驱动。
    - API 层：Android 5.0+ 提供 `android.media.midi`（`MidiManager`、`MidiDevice`、`MidiInputPort`、`MidiOutputPort`）。
    - 应用层：注册 `MidiManager.DeviceCallback` 监听设备插拔，订阅 `MidiOutputPort` 接收 MIDI 消息（`MidiReceiver.onSend`）。
  - **已知兼容性问题**：
    - 部分国产手机（特别是低端机/老旧 ROM）OTG 默认关闭，需用户在设置中手动开启。
    - 部分电钢琴（如卡西欧 CDP 系列）USB MIDI 工作在 Class Compliant 模式，无需驱动；少数老型号需要 Roland/Yamaha 的专有驱动，**v1.0.0 不支持**。
- **风险预警**：
  - 真机测试必须由用户配合：你需要提供至少一台真实电钢琴和一台 Android 手机作为验收环境。**这一项必须在 Version 验收文档中明确标记"需用户配合"**。
  - 部分手机充电与 OTG 不能同时使用（无 OTG hub），长时间练习可能耗尽手机电量。可在 v1.0.0 文档中说明此限制。
- **备选方案**：
  - 备选 B：v1.0.0 同时支持蓝牙 MIDI（BLE-MIDI）。鲁棒性下降（延迟 20-50ms 不稳定，且对手机蓝牙栈兼容性敏感），**不推荐**。
  - 备选 C：v1.0.0 同时支持"无设备模式"（仅触屏，不连电钢琴）。可用于无设备时的功能演示，但偏离核心价值。建议作为"演示/试用模式"加入，详见 F1。
- **用户答复**：
按照建议来吧

### C2. MIDI 文件支持范围【P1】

- **问题描述**：MIDI 文件格式复杂，需要确认 v1.0.0 的支持范围。
- **建议方案**：**支持 Standard MIDI File (SMF) 格式 0 和 格式 1**，单字节编码，识别以下事件：
  - ✅ Note On / Note Off（核心）
  - ✅ Tempo Change（`FF 51 03`）
  - ✅ Time Signature（`FF 58 04`）
  - ✅ Key Signature（`FF 59 02`）
  - ✅ 多轨合并（格式 1 → 合并为单一时间线的 note 序列）
  - ⚠️ Control Change（仅识别 CC 64 延音踏板，其他忽略）
  - ⚠️ Pitch Bend / Aftertouch（忽略，记录到日志但不参与 DK 谱）
  - ❌ SysEx、SMF 格式 2、压缩 MIDI（不支持）
- **风险预警**：
  - 多轨 MIDI 合并时若两个音轨在同一时刻撞键，DK 谱需要去重或保留为"同奏"。建议设计为"同 pitch 的 note 保留最长 duration，去重"。
  - 复杂节奏（如三连音 + 切分音组合）在低 BPM 下视觉密度可能过高，需要在 DK 谱生成阶段做合理可视化。
- **备选方案**：
  - 备选 B：仅支持 SMF 格式 0（单轨）。**不推荐**，绝大多数公开 MIDI 谱面都是格式 1。
- **用户答复**：
按照建议来吧，如果不支持，需要弹窗提示用户，或者做一些兼容性操作

### C3. MIDI 实时输入处理【P1】

- **问题描述**：从电钢琴接收的 MIDI 消息如何与下落 key 进行时间匹配。
- **建议方案**：
  - **判定窗口**：每个 key 在屏幕上"触底"的瞬间为基准时刻 `t0`，判定窗口为 `[t0 - 80ms, t0 + 80ms]`（共 160ms）。窗口内按下对应键 → 通过；早于 `t0 - 80ms` 按 → "抢拍"；晚于 `t0 + 80ms` 仍未按 → 学习模式卡住等待 / 演奏模式记"掉 key"。
  - **延迟补偿**：提供一个全局 `inputLatencyOffset`（默认 0ms，用户可在设置中校准 ±100ms），用于补偿手机 USB MIDI 驱动 + Flutter 平台通道的总延迟。
  - **缓冲策略**：MIDI 事件接收使用独立线程（Android 端 MidiReceiver 回调）→ 通过 EventChannel 推到 Dart 端 → 入队（队列长度 256）→ 主线程在每帧 tick 中消费。
- **风险预警**：
  - 80ms 窗口对娱乐学习足够，但专业演奏者会觉得宽。建议在 v1.0.0 设置中暴露"判定宽度"档位（宽/中/严，160ms/100ms/60ms）。
  - 平台通道延迟可能因机型差异（30-60ms），需要校准功能。
- **备选方案**：固定单一判定窗口（不可调）。**不推荐**，会让部分用户体验下降。
- **用户答复**：
我举得可以

## D. DK 谱与读谱

### D1. DK 谱文件格式【P1】

- **问题描述**：DK 谱需要兼顾"导入导出"、"未来云同步"、"人类可读调试"三方面。
- **建议方案**：**JSON + 顶层版本号，扩展名 `.dk.json`**。结构草案：
  ```json
  {
    "dkVersion": "1.0",
    "meta": {
      "title": "曲名",
      "composer": "作曲家",
      "sourceMidiHash": "sha256...",
      "bpmBase": 120,
      "timeSignature": "4/4",
      "keySignature": "C",
      "totalDurationMs": 180000
    },
    "tracks": [
      {
        "id": "main",
        "notes": [
          { "t": 0, "d": 500, "pitch": 60, "velocity": 80, "hand": "R", "finger": null }
        ]
      }
    ],
    "tempoMap": [ { "t": 0, "bpm": 120 } ]
  }
  ```
  - 时间单位统一为毫秒（`t` = 起始毫秒，`d` = 持续毫秒）。
  - `pitch` 用 MIDI 音高编号（0-127）。
  - `hand` 在 v1.0.0 可选填，若无则 UI 不区分手位。
  - `tempoMap` 支持变速谱面。
- **风险预警**：
  - JSON 体积较大（一首 5 分钟曲可能 200-500 KB），但对手机存储无压力。
  - 未对文件做完整性校验（建议在 meta 中加 `sha256(notes)` 字段）。
- **备选方案**：
  - 备选 B：紧凑二进制格式（类 SMF）。**不推荐**，导入导出调试困难，v1.0.0 价值不大。

## E. 界面与交互

### E1. 钢琴键位数量【P0】

- **问题描述**：电钢琴常见有 49 / 61 / 76 / 88 键，DK 谱与界面键位数需要明确。
- **建议方案**：**界面默认显示 88 键（A0-C8），但实际可视区间为可滚动 32 键左右**（用户可拖动键盘横向滚动，或由 DK 谱自动定位到当前活跃区域）。设置中可选 49/61/76/88 来匹配实际硬件键数。理由：
  - 鲁棒性：MIDI note 范围支持完整 88 键，避免谱面溢出。
  - 可玩性：手机屏幕宽度无法承载 88 键完整显示（每键 4-5mm），必须只显示部分，并跟随当前演奏区域滚动。
  - **可视区滚动策略**：DK 谱预读未来 2 秒的活跃音域，平滑滚动键盘视口居中。
- **风险预警**：
  - 自动滚动可能让用户视觉跟丢。建议设置中提供"自动滚动 / 手动滚动 / 固定视图"三种模式。
  - 32 键视口对宽屏手机略浪费，对窄屏手机略拥挤。建议**视口宽度可设置**（24/32/40 键）。
- **备选方案**：
  - 备选 B：界面固定 61 键全显示（约 4.5cm/键过窄）。**不推荐**，触感差。
  - 备选 C：界面固定 88 键全显示（约 3.5mm/键）。**不推荐**，无法用手指识别。
- **用户答复**：
按照建议方案来吧

### E3. 下落 key 视觉规则【P1】

- **问题描述**：下落速度、宽度、长按表示需要明确，否则原型无法画。
- **建议方案**：
  - **下落速度**：固定"屏幕高度 / 1.5 秒"，即从顶部出现到触底耗时 1.5 秒。BPM 不影响下落速度，**BPM 只影响 key 之间的时间间隔**（更高 BPM = key 之间间距更小 = 屏幕上同屏 key 更多）。
  - **key 宽度**：与对应钢琴键宽度严格对齐，黑键 key 比白键 key 窄 60%，颜色区分。
  - **长按 key**：duration > 200ms 时显示为带尾巴的矩形，尾巴长度 = duration × 下落像素/秒。
  - **同时多 key**：和弦的多个 key 同列下落，触底时刻一致。
- **风险预警**：
  - 1.5 秒下落对快节奏（200+ BPM）曲目会有视觉拥堵。建议**下落时长可在设置中调节（1.0-3.0 秒）**。
  - 长按尾巴在变速段（tempoMap 变化）的视觉处理需要注意，建议在 v1.0.0 简化为"按 base BPM 渲染"。
- **备选方案**：
  - 备选 B：下落速度与 BPM 联动（高 BPM 下落更快）。**不推荐**，会让快节奏不可读。
- **用户答复**：
按照建议方案来吧

## F. 游戏玩法与判定

### F1. 学习模式细节【P0】

- **问题描述**：需求 5 要求学习模式"等用户按到 key 才下一阶段，按错则一直等"，但需要明确：
  - 按错键是否给提示？
  - 等待时下落 key 是停在键面上还是仍在动？

- **建议方案**：
  - **按错处理**：屏幕短暂闪烁红色边框，错误键位高亮红色 0.5 秒；不打断等待，仍可继续尝试正确键。
  - **下落 key 动画**：到达判定线后"停在键面上方"等待，不消失也不下沉，避免用户混淆。
  - **声音来源**：电钢琴本身已发声（用户实际按下电钢琴键），App **不再合成**；学习模式下若希望听到正确示范，提供一个"演示一遍"按钮（独立于学习模式播放）。
  - **同时按错 + 按对**：以"按对"为准进入下一 key，"按错"仅记录到统计但不阻断。
- **风险预警**：
  - 用户的电钢琴未开启 Local Off 时声音正常；若开启了 Local Off（高级用户常用），按键不会发声。建议在 App 启动检测中提示用户确认 Local Off 状态。
  - 没电钢琴的用户在学习模式下完全无法体验。需要在 C1 提到的"触屏代用模式"中决定是否覆盖学习模式（建议不覆盖，仅演奏模式可用触屏）。
- **备选方案**：
  - 备选 B：App 内置 SoundFont 在按键时合成钢琴音。**不推荐**，与电钢琴本身声音叠加会产生回声，且增加音频延迟难题。

### F2. 演奏模式判定与统计【P1】

- **问题描述**：演奏模式按 MIDI 时间线推进，需要明确判定边界和统计口径。
- **建议方案**：
  - **抢拍**：按下时刻 < `t0 - 30ms`（30ms 内视为完美）。
  - **完美**：`|按下时刻 - t0| ≤ 30ms`。
  - **拖拍**：`t0 + 30ms < 按下时刻 ≤ t0 + 80ms`。
  - **掉 key**：到达 `t0 + 80ms` 仍未按。
  - **错音**：按下了不在判定窗口内的其他键，**不计入掉 key，但单独记 ErrorCount**。
  - 演奏结束后给出综合得分（完美 100% / 抢拍 70% / 拖拍 70% / 掉 key 0% / 错音扣分）。
- **风险预警**：
  - 30/80ms 阈值需要在原型阶段用户体验确认，可在设置中暴露。
  - 错音统计在和弦场景下复杂（用户多按一个音），建议 v1.0.0 仅统计单音错音，和弦内错音忽略。
- **用户答复**：
按照建议方案来吧

### F3. BPM 设置范围与变速【P1】

- **问题描述**：需求 6 要求"允许用户设置 bpm，修改后影响演奏快慢"。需要明确范围和单位。
- **建议方案**：
  - **设置方式**：BPM 倍率（0.5x - 2.0x，步进 0.05x）。理由：曲谱本身 tempoMap 已有变速段，倍率方式比绝对 BPM 更直观且与变速谱兼容。
  - **绝对 BPM 显示**：UI 中显示"原 BPM × 倍率 = 当前 BPM"。
  - **音高保持**：仅改变时间速度，不改变音高（与电钢琴本身无关，因为电钢琴是用户实际演奏的，所以这条仅约束 App 内置的"演示一遍"功能）。
- **风险预警**：
  - 2.0x 在 200+ BPM 曲目下手指来不及。可在 UI 上加红色警告，但不阻断。
  - 0.5x 在长曲目下显得过慢，但属于合理学习速度。
- **备选方案**：直接设置绝对 BPM。**不推荐**，与变速谱面冲突。
- **用户答复**：
按照建议方案来吧

### F4. 和弦判定【P1】

- **问题描述**：和弦多键同时按下，需明确容差。
